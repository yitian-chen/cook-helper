# Cook Helper 分阶段实施计划

日期：2026-11-16；状态：P1 已实现，验证详情见 MVP_VALIDATION.md。

## 1. 目标与当前状态

实现带 Web 前端、Python Agent 后端的厨房助手：用户拍摄并上传厨房台面照片，Agent 通过工具识别食材种类与数量、匹配 YAML 菜谱，再生成待买清单和营养分析。用户可配置过敏与忌口，系统在工具执行和最终输出两个层面落实限制。

- 项目位置：当前项目下的 `cook-helper/`。
- 云端仓库：[yitian-chen/cook-helper](https://github.com/yitian-chen/cook-helper)。编写时本地目录与云端仓库均为空。
- Agent 使用 Python 自建 loop，不引入 Agent 编排框架。
- 目标推理模型：用户指定的 `qwen3.8-flash`。已通过用户提供的 OpenAI 格式服务验证文本、原生工具调用和工具回传；不据此推断官方模型命名。
- 视觉识别由独立多模态 API 提供，等待用户后续提供。推理模型与视觉模型使用不同适配器、配置和密钥。
- 当前只实现图片与文本交互；语音输入输出不在本轮范围内。

## 2. MVP 边界与产品流程

MVP 完成一个可运行、可演示的闭环：

1. 配置过敏项、忌口项、用餐人数。
2. 上传照片，显示缩略图与任务状态。
3. Agent 调用 `recognize_ingredients`，返回食材种类、数量、单位及不确定信息。
4. 展示可编辑的识别结果；用户确认或修正后才进入推荐。
5. Agent 调用 `match_recipes`，先执行限制过滤，再加权评分。
6. 前端展示前 3 道候选菜谱、分数依据、已有和缺少的食材、制作步骤。

MVP 提供约 10–15 道经校验的 YAML 菜谱、基础用户偏好持久化及工具执行状态。不包含完整待买清单、营养分析、登录、多用户权限、部署平台或语音功能。

视觉 API 未就绪时，提供固定测试照片和对应模拟数据；界面与响应必须标注 `mock`，不能将任意照片的固定结果当作真实识别。可手动输入食材以验证后续流程。只有真实视觉 API 接入后，才验收“真实照片自动识别”能力。

## 3. 技术设计

建议采用以下工程组合，具体依赖版本在启动开发时选定并锁定：

| 层级 | 方案 | 职责 |
| --- | --- | --- |
| Web | React + TypeScript + Vite | 上传、食材编辑、偏好配置、推荐及清单展示 |
| HTTP API | Python + FastAPI + Pydantic | 请求校验、任务状态、结构化响应 |
| Agent | 自建 Python loop | 消息历史、模型请求、工具调度、终止条件 |
| 模型接入 | 独立推理/视觉适配器 | 隔离服务商协议，支持 mock 和真实实现 |
| 业务工具 | Python 函数 + JSON Schema 注册表 | 识别、匹配、购物清单、营养计算 |
| 配置与数据 | YAML + SQLite | 菜谱、食材字典、用户偏好与任务状态 |
| 校验 | pytest、前端构建及关键流程测试 | 评分、限制、工具行为和集成回归 |

MVP 使用单用户本地模式，后端持有全部 API 密钥。前端轮询任务状态即可；后续按需要增加 SSE。模型生成自然语言解释，确定性业务计算由工具完成。

```text
  docs/IMPLEMENTATION_PLAN.md

```

## 4. 自建 Agent loop

每次运行绑定 `run_id`、用户偏好版本、库存版本和工具结果；服务端注入当前偏好，不能由模型自行忽略或覆盖。

```text
读取请求、已确认库存、最新偏好
→ 构建系统指令和工具 Schema
→ 调用推理模型
→ 若返回 tool_calls：校验名称和参数，检查运行状态，执行并记录结果
→ 将带 tool_call_id 的结果回传模型，继续循环
→ 若识别完成但库存未确认：持久化状态，暂停并返回前端
→ 用户确认后恢复：调用匹配等后续工具
→ 若返回最终答案：校验必需工具是否完成、菜谱 ID 和限制是否有效
→ 返回结构化结果与简短解释
```

模型负责选择工具与解释结果；服务端状态机强制关键前置条件。不能跳过识别/确认直接声称已识别，不能跳过匹配工具编造菜谱。用户手动录入库存是明确允许的另一条入口。

- 工具仅允许注册表内名称，禁止任意代码或 Shell 执行。
- 建议默认最多 8 轮、12 次工具调用；超时和预算可配置，耗尽后明确返回部分结果与停止原因。
- 网络超时、限流可有限重试；参数错误回传结构化错误，连续失败终止，避免无限循环。
- 状态包含 `queued/running/awaiting_confirmation/completed/failed/cancelled`；确认接口只能恢复等待中的任务，并校验版本。
- 工具日志记录调用名、耗时、状态和脱敏摘要，不展示模型内部思维过程，不记录密钥或图片 Base64。
- 菜谱与图片中的文本均作为数据处理，不能修改系统指令或用户限制。
- 推理服务若不支持原生 tool calling，先评估并明确实现受 Schema 校验的 JSON 调用协议；不能默认不同服务商完全兼容。

## 5. 工具契约

工具统一返回 `{ok, data, error, warnings}`；错误含稳定 `code` 与可读说明。所有食材使用标准 `ingredient_id`，保留原始名称用于展示。

| 工具 | 主要输入 | 主要输出 |
| --- | --- | --- |
| `recognize_ingredients` | 服务端 `image_id` | 食材 ID/名称、数量、单位、可选置信度、不确定项、provider 模式 |
| `match_recipes` | 已确认库存引用、人数；服务端偏好 | 合规候选、评分分项、缺料与缺量、排除原因 |
| `generate_shopping_list` | 已选菜谱 ID、各自份数、库存引用 | 合并待买食材、数量、单位、来源菜谱、待确认项 |
| `analyze_nutrition` | 已选菜谱 ID、各自份数 | 整餐及每人热量、蛋白质、脂肪、碳水，来源、覆盖率与估算说明 |

照片只能估计可见物体数量；不能据此准确推断重量、包装余量、隐藏食材或新鲜度。无法判断数量时返回 `null`，由用户确认；供应商不提供可信置信度时不伪造数值。

## 6. 数据与算法

### 6.1 YAML 菜谱

示例仅说明结构，实际食材重量与营养数据在配置阶段审核：

```yaml
schema_version: 1
id: tomato_egg
name: 番茄炒蛋
servings: 2
time_minutes: 15
tags: [家常, 快手]
ingredients:
  - ingredient_id: tomato
    amount: 300
    unit: g
    role: main
    optional: false
  - ingredient_id: egg
    amount: 2
    unit: piece
    role: main
    optional: false
  - ingredient_id: cooking_oil
    amount: 10
    unit: g
    role: seasoning
    optional: false
  - ingredient_id: salt
    amount: 2
    unit: g
    role: seasoning
    optional: false
steps:
  - 番茄切块，鸡蛋打散。
  - 锅中加油，炒熟鸡蛋盛出。
  - 炒软番茄，加入鸡蛋与盐翻炒。
```

加载时使用安全 YAML 解析并执行 Schema 校验：ID 唯一、份数为正、数量合法、单位受支持、食材引用存在。过敏原由标准食材字典推导，复合调料须包含组成或过敏原信息。无法归类的食材不能被当成已确认安全。

### 6.2 加权匹配

先硬过滤过敏与忌口，再排序。过敏和忌口不能以扣分替代过滤；人数用于线性缩放需求量。

MVP 建议：主料权重 3、辅料 2、调味料 1，可配置。对每项必需食材定义：

- `p_i`：库存中存在该食材为 1，否则 0。
- `a_i`：单位可换算时为 `min(库存量 / 需求量, 1)`；未知或不可换算时暂取 0，并标为待确认，不能声称一定缺料。
- `C = Σ(w_i × p_i) / Σw_i`：种类覆盖率。
- `A = Σ(w_i × a_i) / Σw_i`：数量满足率的保守估计。
- `score = 100 × (0.7 × C + 0.3 × A)`。

例：两项主料都存在但只有一项足量，另一项完全缺量时，`C=1、A=0.5`，得分 85。真实展示同时说明缺量，不将高分等同于可直接做。

可选食材不纳入基础分母，但若实际使用仍须限制校验。同分按缺少必需食材种类更少、制作时间更短、菜谱 ID 排序。默认不假设用户拥有油盐等调料；可显式勾选“常备调料”。无合规菜谱时返回空结果与原因，不放宽限制。

### 6.3 待买清单

按菜谱份数缩放 → 按标准 ID 与兼容单位合并全部需求 → 库存只扣减一次 → `待买量=max(总需求量-库存量, 0)`。不能逐道菜重复扣减同一库存。单位不可换算、数量未知时输出待确认项；包装采购取整作为后续增强。

### 6.4 营养分析

依据菜谱用量与食材每 100g 数据确定性计算，再汇总整餐与每人结果。件数到克数使用有来源的食材换算配置并标注估算；缺失重量或营养值不按零处理，输出可计算部分及缺失列表。营养表必须记录来源、版本、可食部口径；MVP 后的首版只做估算，不宣称医学建议或过敏安全认证。

### 6.5 过敏与忌口

偏好至少包含 `allergens`、`excluded_ingredient_ids`、`dietary_rules`、`servings`。自然语言输入转换后由用户确认；未映射文本不能静默丢弃。过敏原使用标准分类，忌口按明确食材或规则执行，不将文化或宗教饮食规则简化为任意猜测。

菜谱匹配、待买清单、替换建议和最终输出共享同一限制检查。修改偏好会使已有推荐失效并重新计算。含未知组成的复合食材在相关过敏限制下排除或要求确认；页面提示包装标签及交叉接触风险无法通过照片排除。

## 7. 分阶段与分支计划

采用稳定 `main` + 短期 feature 分支；前一阶段验收并合并后，再从最新 `main` 开下一分支。每个分支保持可独立审查、可回退。P1 已在 feat/mvp 分支实施并分批提交；尚未合并主分支或推送。

| 阶段 / 分支 | 工作范围 | 验收条件 |
| --- | --- | --- |
| P0 `docs/implementation-plan` | 计划、模型接口待确认项、工程约定 | 范围与接口清晰，确定 MVP 与完整目标差异 |
| P1 `feat/mvp` | 前后端骨架、自建 loop、推理适配器、mock 识别、确认页、YAML 菜谱、加权匹配、基础偏好 | 本地一键启动；固定照片完成闭环；真实推理调用通过；限制过滤生效；无密钥也有明确 mock 演示模式 |
| P2 `feat/vision-provider` | 接入用户提供的多模态 API、结构化解析、真实照片测试 | 真实上传照片得到种类与数量；低确定性可修正；超时/错误可恢复；不再以 mock 作为真实识别验收 |
| P3 `feat/shopping-list` | 菜谱多选、份数调整、库存合并扣减、清单勾选 | 多菜重复食材正确合并；单位冲突可见；修改选择重新生成；输出符合限制 |
| P4 `feat/nutrition-analysis` | 营养数据源、单位换算、整餐/每人展示 | 已知样例计算正确；份数变化一致；缺数据不虚构；来源与估算可见 |
| P5 `feat/dietary-preferences` | 扩充别名与复合食材映射、饮食规则编辑、限制解释 | 同义食材和复合调料被正确拦截；偏好更新使旧结果失效；所有输出工具共用限制策略 |
| P6 `feat/reliability-and-demo` | 任务取消与恢复、可选 SSE、上传清理、配置文档、端到端演示 | 真实照片到推荐/清单/营养的完整流程通过；异常路径可理解；部署步骤可复现 |

P1 内部按“工程骨架 → 配置和数据模型 → 工具与测试 → loop → 前端 → 联调”分批提交。P5 是扩展阶段，不能成为推迟 P1 基础过敏与忌口过滤的理由。若视觉 API 暂未提供，P2 保持待接入，可先从已合并的 P1 开 P3/P4，使用相同工具契约推进。

建议里程碑：P1 合并标记 `v0.1.0-mvp`；P2–P5 完成标记 `v0.2.0`；P6 验收后标记 `v1.0.0-demo`。

## 8. Git 与验收流程

空仓库首次开发时先建立 `main` 的基础提交，再创建工作分支；如果本地尚未连接远端，先确认 Git 根目录和 remote，避免误将整个课程项目提交到 cook-helper 仓库。

日常流程示例（文档说明，不代表已执行）：

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/shopping-list
# 开发，执行检查，提交
git push -u origin feat/shopping-list
# 创建 PR，验收并合并后删除功能分支
```

每个 PR 说明：解决的场景、交互变化、工具与 Schema 变化、验证结果、已知限制。每次合并至少执行后端相关测试、菜谱配置校验、前端类型检查和构建；涉及交互时完成对应冒烟流程。API 和 Schema 变化同步更新调用方、fixture 与文档。

关键回归集：

1. 已有番茄与鸡蛋时评分、排序和分项正确且稳定。
2. 鸡蛋过敏时，含蛋及相关复合食材的菜谱不出现在结果中。
3. 无合规菜谱、未知食材、未知数量、全部识别失败有明确状态。
4. 模型返回未知工具、非法参数、跳过匹配或无限请求时服务端能拦截并终止。
5. 两道菜共用库存时购物清单不重复扣减；单位不兼容不强行相加。
6. 营养缺项、件重估计、份数缩放有可核对的结果。
7. 偏好修改后旧任务结果不能覆盖新配置对应的结果。
8. 上传限制文件大小和类型，验证实际图片内容，图片 ID 不能越权访问任意本地路径。

视觉集成阶段选取约 20 张有人工标注的厨房照片，统计食材种类准确率/召回率和可数物体数量误差；透明容器、遮挡、包装和散装分别记录。先建立基线，再根据实际模型能力确定可接受阈值，不预先承诺识别准确率。

## 9. 接口与待提供信息

建议 HTTP 边界：`POST /api/images`、`GET/PUT /api/preferences`、`POST /api/runs`、`GET /api/runs/{id}`、`POST /api/runs/{id}/confirm-inventory`、`POST /api/runs/{id}/cancel`。后续清单和营养请求通过已选菜谱触发 Agent 调用对应工具，结果保留工具来源，不单靠聊天文本解析。

环境配置包括 `REASONING_BASE_URL`、`REASONING_API_KEY`、`REASONING_MODEL`、`VISION_PROVIDER`、`VISION_BASE_URL`、`VISION_API_KEY`、`VISION_MODEL`。密钥只放本地环境或部署密钥管理中，`.env.example` 仅写占位符；上传图、SQLite、运行日志不入 Git。

真实对接前需要：

- 推理 API：服务商地址、鉴权方式、实际模型 ID、工具调用与结构化输出样例。
- 多模态 API：地址、模型 ID、鉴权方式、图片传输方式、请求/响应样例、大小限制和限流信息。
- 营养阶段：允许使用的数据来源和适用范围；未确定前只用明确标注的测试数据验证计算。

以上不阻塞工程骨架、模拟工具和业务算法开发；缺少真实模型凭据时对应集成验收保持未完成。后续语音只作为输入转文本和结果转语音的适配层接入，复用现有任务、工具和限制逻辑。
